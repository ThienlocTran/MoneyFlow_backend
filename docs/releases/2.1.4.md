# MoneyFlow 2.1.4

Status: BACKEND LOCKED / AZURE LOCAL SETUP DOCUMENTED

Release target: backend Receipt OCR foundation.

## Boundary

2.1.4 is planned as a backend-first receipt OCR/image-to-draft release. P11F adds explicit receipt draft confirm into posted transactions with receipt evidence links.

## Non-Negotiables

- Receipt OCR is draft-first.
- OCR text/image are evidence, not final truth.
- No receipt OCR result auto-posts a transaction.
- Confirm is required before ledger mutation.
- Expense wallet/category rules are preserved.
- Storage failure does not block review/confirm when OCR/manual text can proceed.
- No fake OCR financial data in runtime paths.
- Workspace membership is required for all receipt session/draft access.

## P11D Implemented

- Real `azure_document_intelligence` provider using Java `HttpClient`.
- Azure REST API version: `2024-11-30`.
- Default model: `prebuilt-receipt`.
- Config placeholders: `AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT`, `AZURE_DOCUMENT_INTELLIGENCE_KEY`, `AZURE_DOCUMENT_INTELLIGENCE_MODEL_ID`, `AZURE_DOCUMENT_INTELLIGENCE_API_VERSION`.
- Local setup guide: `docs/receipt-ocr/azure-document-intelligence-setup.md`.
- Local resource endpoint: `https://moneyflow-doc-intelligence.cognitiveservices.azure.com`.
- Local smoke still requires a real key in `.env`; the key must never be committed.
- Session request strategy: stored image URL sent as Azure `urlSource`; bytes are used when callers provide them.
- Polls `Operation-Location` until success, failed result, timeout, or max attempts.
- Maps raw OCR text, merchant, receipt date, total amount, and currency into receipt session fields.
- Maps missing config, auth, rate limit, timeout, bad request, missing text, missing total/date, and provider failure warnings.
- Tests use mocked HTTP/fake local HTTP server only.
- No draft builder, no confirm-to-transaction, no frontend UI.

## P11E Implemented

- `POST /api/workspaces/{workspaceId}/receipt-sessions/{sessionId}/drafts`
- `receipt_session_drafts` persistence.
- Detail responses include drafts.
- One primary expense draft is built from OCR structured fields/text.
- Amount parsing uses the Java receipt amount candidate ranker.
- Vietnamese total labels such as `Phải thanh toán`, `Tổng cộng`, `Tổng thanh toán`, `Cần thanh toán`, `Thành tiền`, and `Tổng tiền` beat larger numeric tokens.
- Rounded cash/payment labels are secondary candidates.
- Customer tendered, change returned, loyalty points, receipt codes, phones/hotlines, dates/times, quantities, VAT, and percent contexts are excluded.
- Largest-number selection is forbidden.
- Date parsing handles simple receipt dates.
- Category is hint-only; wallet is not guessed.
- Rebuild replaces current session drafts to avoid duplicates.
- P11E itself did not confirm to transaction; P11F adds confirm. No frontend UI.

## R-OCR-2 Hotfix

- Bách Hóa Xanh receipt target behavior: primary `67463`, secondary `65000`, excluded `200000`, `135000`, `2463`, `6359148`, and `18001067`.
- Azure structured `Total` with good confidence is preferred; low-confidence structured total falls back to label-aware text ranking.
- Stateless receipt review now exposes backend amount candidate evidence for future UI review.
- If no safe amount exists, the draft/review keeps amount missing instead of choosing a random largest number.

## R-OCR-3 Hotfix

- Merchant/date/category extraction is confidence-first and review-first.
- Azure structured merchant/date fields win only with acceptable confidence; otherwise text candidates are ranked.
- Merchant extraction rejects time, date, amount, phone, hotline, receipt code, staff, VAT, QR, and footer contexts.
- Date extraction handles common receipt date formats and rejects phone/hotline/code noise.
- Category suggestion uses same-workspace merchant history first, then unique active grocery/food category matches.
- Random category autofill is forbidden.
- Shipper/delivery categories require explicit delivery evidence.
- Bach Hoa Xanh receipt behavior: amount `67463`, merchant `Bách Hóa Xanh`, date `2026-07-30`, no shipper category without delivery evidence.
- Archived categories and cross-workspace category/history data are ignored.

Known limitations:

- Frontend candidate picker remains R-OCR-4.
- More real receipt fixtures remain R-OCR-5.
- Category learning can be improved later with more confirmed receipt data.

## P11F Implemented

- `POST /api/workspaces/{workspaceId}/receipt-sessions/{sessionId}/drafts/{draftId}/confirm`
- Confirm requires amount, date, wallet, category, same-workspace session/draft, and same-workspace wallet/category.
- Confirm returns warning responses for user-correctable draft issues and creates no transaction on validation failure.
- Confirm creates a posted `EXPENSE` through the existing transaction service path.
- Transactions use `sourceType=RECEIPT` and link `receiptSessionId` plus `receiptSessionDraftId`.
- Drafts store `confirmedEntityType`, `confirmedEntityId`, and `confirmedAt`.
- Repeated confirm is idempotent and returns the existing transaction.
- Session status becomes `PARTIALLY_CONFIRMED` or `CONFIRMED`.
- Upload, OCR, and draft build remain no-auto-save.
- Backend tests cover success, warnings, idempotency, partial status, workspace isolation, invalid wallet/category, and no-auto-save regression.
- No frontend UI yet.

## Known Limitations

- Frontend receipt UI is not implemented in this backend release.
- Live Azure OCR still requires user-provided Azure Document Intelligence key/resource.
- OCR quality varies by receipt photo quality.
- Missing amount, date, category, or wallet requires user review.
- Line-item splitting into multiple transactions is deferred.
- Storage disabled means receipt can still process when OCR/text is available, but image evidence playback/display may be unavailable.
